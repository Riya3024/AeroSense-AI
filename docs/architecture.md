# AeroSense AI - architecture

Target AWS region: **ap-south-1 (Mumbai)**. Status as of this document: **nothing is deployed to AWS. The Phase 2 data pipeline is implemented and tested on synthetic data but has not yet been run against the live APIs or a real S3 bucket.**

## 1. What the product does (MVP)

A user enters *from*, *to*, *departure time* and *travel mode*. AeroSense should (eventually):

1. obtain real environmental data,
2. predict near-term PM2.5,
3. compare route alternatives,
4. estimate pollution exposure per route,
5. recommend the lower-exposure option,
6. explain why.

### Service roles

| Service | Role | Decision state |
|---|---|---|
| **S3** | One bucket; `aerosense/raw/air_quality`, `raw/weather`, `processed/delhi_hourly/<START>_<END>/`, `reports/<START>_<END>/`, later `models/` | Script ready (`create-s3-bucket.ps1`), uploader ready (`upload_s3`); neither run |
| **SageMaker** | Training jobs (and possibly hosting) | Role/policy template ready; nothing created |
| **Lambda** | Runs `backend/handler.py` behind the API | Handler exists (`/health` only); not deployed |
| **API Gateway** | HTTP API in front of Lambda | Handler accepts both v2 and v1 proxy events; not created |
| **CloudWatch** | Lambda logs, training logs, metrics; retention via `CLOUDWATCH_LOG_RETENTION_DAYS` | Log-group permissions in the Lambda policy template |
| **Amplify** | Hosts the future frontend | Only the CORS origin setting (`API_ALLOWED_ORIGIN`) is prepared |
| **DynamoDB** | **Not needed for the MVP.** | Add only if a concrete need appears, e.g. caching route results or storing user history. `DYNAMODB_TABLE_NAME` is an optional setting for that day. |

### Security model

* No credentials in the repo. Locally: AWS CLI profile or SSO (`aws configure` / `aws sso login`).
  In AWS: IAM execution roles. `backend/settings.py` deliberately has no access-key handling.
* `.env` is git-ignored (as are `.env.*` except `.env.example`, `.aws/`, `*.pem`, `*.tfstate`, `credentials*`).
* A test scans the repository for AWS key IDs, secret assignments and private-key blocks.
* IAM templates are scoped to `ap-south-1`, the project bucket prefixes, `aerosense-*` log groups and endpoints.
  They are templates for you to review, not audited policies.
* The health endpoint returns no bucket names, account IDs or endpoint names (tested).

## 5. Configuration

Two independent settings objects, both read from environment variables (and a local `.env`):

| Object | Configures | Variables |
|---|---|---|
| `data_pipeline.config.Settings` (existing) | ingestion and cleaning | `OPENAQ_API_KEY`, `DELHI_BBOX`, `START_DATE`, `END_DATE`, ... |
| `backend.settings.AppSettings` (new) | the deployed application / AWS | `AEROSENSE_ENV`, `AWS_REGION`, `AEROSENSE_S3_BUCKET`, `SAGEMAKER_ROLE_ARN`, `SAGEMAKER_ENDPOINT_NAME`, `DYNAMODB_TABLE_NAME`, `CLOUDWATCH_LOG_RETENTION_DAYS`, `API_ALLOWED_ORIGIN` |

Every backend variable is optional at import time. `AppSettings.missing_for("sagemaker")` tells a script
exactly what is still unset. A test enforces that every variable the backend reads is documented in `.env.example`.

## 6. Known gaps and risks to resolve before the MVP works end to end

1. **The pipeline is historical-only.** It uses the Open-Meteo *archive* (ERA5, ~5 day lag) and a fixed
   date range. A live recommendation needs (a) the latest PM2.5 and its recent lags for stations at request time
   (or a scheduled ingestion job writing to S3) and (b) a weather *forecast* source for the departure time.
   The README already warns that forecast features need Open-Meteo's Historical *Forecast* API for training so
   train and serve distributions match. This is the largest design item for Phase 3.
2. **Model horizon.** The current target is PM2.5 at t+1h. Departure times further out need either a longer
   horizon target or an explicit statement that predictions only cover the next hour.
3. **Phase 2 data hygiene facts to respect in Phase 3:** timestamps are UTC hour-ending; calendar features are IST; pollutants are never imputed; weather may be forward-filled up to 3 h (flagged in `weather_imputed_count`).
3b. **Station-to-route exposure.** Stations are points; routes are lines. How PM2.5 is interpolated along a route
   is undecided and is part of the (not yet started) route engine.
4. **Model hosting cost/complexity.** A SageMaker real-time endpoint bills while it runs. For a small tabular
   model, loading the artifact from S3 inside Lambda may be simpler for a hackathon. Decide in Phase 2 once the
   model type and size are known.
5. **Live APIs unverified.** OpenAQ field names, the `datetime_from/to` parameters and the PM2.5 parameter name
   are taken from documentation and have not been exercised against the real service (see the README checklist).
6. **Coverage.** Delhi station count and data completeness are unknown until the first live pull.

## 7. Deployment roadmap

| Phase | Goal | AWS resources |
|---|---|---|
| 1 (this change) | Foundation: structure, config, docs, tests | none |
| 2 | Real Delhi data -> hourly ML dataset -> quality report -> S3 (code done; first real run pending) | S3 bucket |
| 3 | PM2.5 baseline + first model trained on the Phase 2 dataset; real metrics only | SageMaker role/training job (or train locally first) |
| 4 | Live data path + route engine + exposure estimate + recommendation endpoint | Lambda, API Gateway, CloudWatch; optionally SageMaker endpoint |
| 5 | Frontend and explanation UI | Amplify |
| 6 | Hardening: alarms, cost review, load test | CloudWatch alarms; DynamoDB only if justified |
